# 统一支付业务工作台完整目标规格

## 1. 产品定位

工作台是统一支付业务诉求的交互投影，不是任一后端接口的可视化包装。它面向三类使用者：

- 商户与业务人员：创建和查询支付、推进支付、申请退款、查看结果；
- 渠道模拟者：在 reference/sandbox 环境提交渠道结果并观察重复、未知、迟到和冲突语义；
- 平台运营与学习者：查看支付尝试、退款预算、对账差异、结算构成、人工处置和全链路证据。

业务目标覆盖支付创建、支付尝试、渠道结果、退款、对账、结算、通知和审计轨迹。后端尚未提供的目标能力仍保留在统一模型和对齐清单中，但界面不得伪造可执行结果。

## Requirements

### Requirement: 统一业务契约与适配器隔离

系统必须以统一支付业务模型和服务作为页面唯一依赖，通过能力与动作声明表达后端现状，并由适配器封装两套后端的传输和语义差异。

#### Scenario: 同一页面切换两个后端

- GIVEN 工作台分别使用 WOW 或 CAP4K 配置启动
- WHEN 用户进入同一组业务页面
- THEN 页面只调用统一服务并依据统一能力与动作声明渲染
- AND 切换后端不修改页面代码
- AND 源路径、字段、状态、金额和错误差异均由适配器处理

### Requirement: 创建和查询支付

系统必须支持按统一业务字段创建支付、按支付号查询详情，并使用精确金额模型保留幂等与源状态语义。

#### Scenario: 创建后查看统一支付详情

- GIVEN 用户填写商户、订单号、幂等键、精确金额、币种、支付方式和可选到期时间
- WHEN 用户提交创建并查询返回的支付号
- THEN 页面显示统一支付详情、源状态、幂等复用结果和可执行动作
- AND 金额不经过 JavaScript 浮点计算
- AND 创建受理不显示为已经付款

### Requirement: 支付尝试与渠道结果收敛

系统必须兼容 WOW 创建时启动尝试和 CAP4K 显式启动尝试的现状，同时保持支付、尝试和渠道回执三个业务概念独立。

#### Scenario: 按当前适配器推进支付结果

- GIVEN 某支付在当前适配器下存在可执行的支付动作
- WHEN 用户发起尝试或通过渠道模拟提交成功、失败、未知、重复或冲突结果
- THEN 工作台按该后端实际流程执行并查询最终读模型
- AND 分别展示支付主状态、尝试状态、回执处置与证据
- AND 不把已受理、HTTP 2xx 或命令成功显示为支付成功

### Requirement: 退款闭环

系统必须允许对成功支付发起全额或部分退款，并展示预算占用、成功累计、可退款余额、结果收敛和人工裁决。

#### Scenario: 创建并推进退款

- GIVEN 支付已成功且存在可退款金额
- WHEN 用户创建全额或部分退款并按当前适配器支持的方式推进结果或人工裁决
- THEN 工作台显示退款状态、源状态、成功金额、占用金额、可退款金额和错误原因
- AND 可以从支付详情追踪相关退款

### Requirement: 对账、结算与全链路操作

系统必须为对账、结算和支付轨迹提供统一业务视图，并只启用当前适配器真实支持的查询和操作。

#### Scenario: 按能力操作运营流程

- GIVEN 当前适配器声明了某项对账、结算或追踪能力
- WHEN 用户按 ID 查询或执行重跑、处置、准备、确认、执行、结果、替代或裁决动作
- THEN 页面显示统一事实、证据、阻断原因和可执行动作
- AND 未支持动作明确显示待对齐原因而不发送请求

### Requirement: 状态、错误与异步反馈

系统必须区分统一业务状态、源状态、操作受理和最终状态，并将两套错误结构归一为可操作的反馈。

#### Scenario: 请求失败或等待最终一致状态

- GIVEN 请求可能加载、为空、失败、冲突、未找到或最终一致收敛
- WHEN 任一情况发生
- THEN 页面保留输入和当前上下文
- AND 展示标准化错误码、可读消息、字段问题、可重试性及源诊断
- AND 异步操作明确区分受理回执、轮询状态和业务终态

### Requirement: 最近记录与目标分页契约

系统必须在没有后端列表接口时提供本地最近记录导航，同时保留统一分页查询目标并避免把本地数据冒充后端全量数据。

#### Scenario: 使用最近记录重新打开资源

- GIVEN 两个后端当前都没有权威支付或退款列表和分页接口
- WHEN 用户创建或成功查询业务对象
- THEN 工作台把其最小导航信息写入当前适配器的浏览器最近记录
- AND 用户可以再次打开或移除记录
- AND 页面明确说明它不是后端全量列表
- AND 统一分页契约与两端缺口出现在对齐清单中

### Requirement: 业务能力与后端对齐清单

系统必须以统一业务诉求为基准，逐项说明两个后端的当前能力、工作台兼容策略和后端后续迭代要求。

#### Scenario: 查看可执行的后端对齐项

- GIVEN 统一业务诉求和两个后端现状存在差异
- WHEN 用户查看能力对照页或维护者阅读对齐文档
- THEN 能看到目标语义、WOW 现状、CAP4K 现状、工作台处理、缺失能力、建议改动和优先级
- AND 至少覆盖列表分页、支付发起、退款结果、对账入口、结算流程、轨迹、认证授权和浏览器接入

### Requirement: 工作台交互可用性

系统必须让业务用户在桌面和移动视口清晰完成商户操作、渠道模拟和平台运营流程，并对危险动作、长标识和动态状态提供稳定交互。

#### Scenario: 在不同视口完成主要操作

- GIVEN 用户在桌面或移动视口使用工作台
- WHEN 在三类业务视角间导航并提交表单
- THEN 页面信息层次清楚、控件不重叠且长标识可阅读
- AND 危险或不可逆动作有明确确认
- AND 加载、空、错误和成功反馈不会造成布局错乱

### Requirement: 可运行与可扩展交付

系统必须提供完整的运行配置、自动化验证和维护文档，使开发者能够切换两个后端并新增第三种适配器。

#### Scenario: 按文档运行两种模式

- GIVEN 开发者获得仓库
- WHEN 按 README 安装并分别运行 WOW 与 CAP4K 模式
- THEN 应用可以启动、构建和测试
- AND 开发代理连接对应后端
- AND README 说明目录、配置、切换、统一契约、业务流程、差异、限制及新增第三适配器步骤

## 2. 统一领域契约

### 2.1 共同基础类型

- `Money`：`currency` 与以字符串承载的最小单位金额；显示层可接受十进制字符串输入，但必须通过币种精度转换，禁止浮点运算。
- `PageRequest` / `PageResult<T>`：定义页码、页大小、总数、是否有下一页和可选游标，作为目标查询契约；没有源接口时能力声明为不可用。
- `OperationReceipt`：资源标识、操作是否受理、是否幂等复用、源状态、建议刷新策略和可选诊断。它不等于业务终态。
- `BusinessError`：标准码、用户消息、字段错误、HTTP 状态、可重试性、源码、源消息和关联信息。
- `SourceMetadata`：适配器、源状态、源标识、源时间与可选原始诊断，用于学习和排错。
- `ActionDescriptor`：业务动作、是否可执行、禁用原因、所需字段、确认级别和执行后的刷新策略。
- `CapabilityDeclaration`：查询、命令、模拟、追踪、列表/分页、人工处置等能力的 `full / partial / unavailable` 状态和原因。

### 2.2 支付

`Payment` 至少包含平台支付号、商户、商户订单号、幂等信息、金额、币种、支付方式、创建/到期/成功/关闭时间、统一状态、源状态、渠道交易号、退款金额摘要、支付尝试、复核摘要、结算资格、源信息和可执行动作。

统一支付状态：`PENDING`、`PROCESSING`、`SUCCEEDED`、`FAILED`、`CLOSED`、`PENDING_CONFIRMATION`。`RESULT_UNKNOWN` 映射为 `PENDING_CONFIRMATION`，但保留源状态。

`PaymentAttempt` 独立保存尝试标识、渠道、请求身份、状态、发起时间、渠道交易号、最终结果、回执证据和源信息。支付状态、尝试状态和渠道回执处置是三个不同概念。

### 2.3 退款

`Refund` 至少包含退款号、商户退款号、原支付号、金额、币种、统一状态、源状态、渠道退款号、尝试、回执、预算占用、复核和源信息。

统一退款状态：`REQUESTED`、`PROCESSING`、`SUCCEEDED`、`FAILED`、`REJECTED`、`PENDING_CONFIRMATION`。WOW 的 `CREATED` 映射为 `REQUESTED`，两套后端的 `RESULT_UNKNOWN` / `REVIEW_REQUIRED` 按是否已进入人工处置分别映射并保留源状态。

支付详情必须显示支付成功金额、成功退款累计额、处理中占用额和当前可退款金额；缺少源字段时显示未知，不自行推算成权威事实。

### 2.4 对账与结算

对账模型包含批次范围、账单身份与 revision、运行历史、明细、差异分类、处置、阻断原因和源证据。统一差异类型覆盖匹配、平台单边、渠道单边、金额/币种/状态差异、重复和无法关联。

结算模型包含商户、币种、周期、支付收入、退款扣减、手续费、调整、净额、明细来源、确认冻结、执行尝试、结果回执、复核和 replacement/void 关系。

统一视图只归一业务含义，不抹平 WOW 的自动流程与 CAP4K 的显式分步流程。

## 3. 统一服务与适配器

### 3.1 服务边界

页面只能依赖组合后的 `PaymentWorkbenchService`，其业务能力包括：

- 读取连接信息和能力声明；
- 创建、查询和分页查询支付；
- 在允许时发起支付尝试、提交 reference 渠道结果、显式到期和裁决复核；
- 创建、查询和分页查询退款，提交 reference 渠道结果或裁决；
- 查询支付全链路轨迹；
- 查询/重跑/处置对账，在 reference 入口允许时登记账单并触发对账；
- 查询、生成/准备、确认、执行、提交结果、裁决、作废或替代结算；
- 统一轮询最终状态、错误和源诊断。

列表服务属于目标契约。适配器不能实现时返回能力不可用，页面改用本地最近记录，不能通过抓取日志或扫描内存伪造列表。

### 3.2 WOW 适配器

WOW 适配器负责：

- 把统一创建字段映射到 `/api/payments`，把最小单位字符串在安全范围内转换为后端 `Long`；
- 将创建后由后端自动选择配置并启动尝试的流程表达为当前支付动作，而不虚构独立 start endpoint；
- 把 reference 支付结果映射到 `/api/payments/{paymentId}/results`；
- 把支付下退款创建映射到 `/api/payments/{paymentId}/refunds`，并说明结果参数会驱动 fake adapter；
- 处理退款和结算裁决、Fake 权威账单、bill-available、结算生成/替代/裁决、支付 trace、通知和配置查询；
- 将轻量命令响应视为受理回执，按资源类型轮询 Projection 直到目标状态或超时；
- 把 `{code,message,field?}`、HTTP 400/404/409 和网络错误映射为统一错误；
- 明确列表/分页、生产认证、持久化读库和浏览器 CORS 当前不可用。

### 3.3 CAP4K 适配器

CAP4K 适配器负责：

- 把统一创建字段映射到 `/api/payments`，将最小单位字符串精确转换为后端十进制金额；
- 将显式支付尝试映射到 `/api/payments/{paymentId}/attempts`；
- 将 reference 渠道支付、退款和结算结果分别映射到对应 `/api/channel/*-results`，sandbox 校验材料来自集中配置；
- 将退款创建映射到 `/api/refunds`；
- 支持按 ID 查询支付、退款、对账批次和结算；
- 支持对账重跑与差异处置，以及结算准备、确认、执行和受控作废；
- 把 `{status,code,message,details}`、HTTP 400/404/409/500 和网络错误映射为统一错误；
- 明确对账批次由调度/集成事件形成、没有普通前端创建入口；列表/分页、生产认证和浏览器 CORS 当前不可用。

### 3.4 适配器选择

适配器由集中配置工厂创建。至少提供 WOW 与 CAP4K 两个开发模式及对应代理目标。页面、组件、hooks 和表单不得读取适配器名称来决定业务流程；只读取领域对象的 `actions` 与能力声明。

新增第三种后端只需新增适配器、映射测试和配置注册；若统一业务契约没有新增业务语义，不修改已有页面。

## 4. 业务流程

### 4.1 创建与查找支付

创建表单收集商户、订单号、幂等键、金额、币种、支付方式和可选到期时间。创建成功后进入支付详情，显示“收款意图已受理”，不能显示“已付款”。幂等复用要明确提示；冲突保留表单值并展示原因。

两端没有列表能力时，首页和支付入口显示本地最近访问的支付。用户也可以输入支付号直达详情。

### 4.2 支付尝试和渠道模拟

支付详情根据动作声明展示发起尝试、模拟成功、失败、未知、重复/冲突、到期或人工裁决。WOW 可在创建后直接进入已启动尝试；CAP4K 需要先显式发起尝试。工作台兼容两种现状，但能力对照明确指出目标业务契约要求独立支付尝试入口和身份。

每次操作先显示受理结果，再刷新详情。页面同时显示统一状态、源状态、支付尝试和渠道回执处置；`ACCEPTED`、HTTP 2xx 或命令 accepted 均不得当作支付成功。

### 4.3 退款

成功支付详情提供退款入口。表单默认显示当前可退款金额，支持全额和部分退款，收集商户退款号、幂等键、金额、币种和原因；源后端缺少某字段时适配器声明语义缺口，并在对齐清单记录，页面仍保留统一业务字段。

退款结果推进按适配器动作执行：WOW 在创建时选择 fake 结果并对未知结果提供裁决；CAP4K 创建后由独立 sandbox 渠道结果推进。详情必须显示预算占用、成功累计、失败释放和未知继续占用的业务语义。

### 4.4 对账

对账页面支持按批次 ID 查询。WOW 在 reference 模式下可登记 Fake 权威账单并触发 bill-available；CAP4K 对已有批次支持查询、重跑和差异处置。页面展示 revision、运行、明细、差异、证据、处置和结算阻断。

没有能力的入口显示“当前后端待对齐”及原因，不隐藏统一目标，也不伪造批次。

### 4.5 结算

结算页面支持按 ID 查询。WOW 支持从有效对账事实生成、自动推进、替代和裁决；CAP4K 支持准备、确认、执行、结果和受控作废。页面以可执行动作描述两种流程，展示金额恒等式、明细来源、冻结、未知结果禁止重付、负净额人工处理和替代链。

### 4.6 全链路与能力对照

WOW 提供统一 trace endpoint 时展示完整支付轨迹。CAP4K 没有统一 trace endpoint 时，从支付查询中展示已提供的尝试、通知和 review，并将跨退款/对账/结算的统一 trace 列为对齐项；不得通过猜测 ID 拼接成权威轨迹。

能力对照页同时展示目标流程、当前适配器能力和两个后端差异，帮助学习实现边界。

## 5. 页面与交互

- 工作台首页：当前后端、健康/连接状态、能力摘要、业务流程导航、本地最近记录和对齐提示。
- 支付区：创建、按 ID 查找、支付详情、尝试/回执、退款摘要、可执行动作。
- 退款区：按 ID 查找、退款详情、结果推进与裁决。
- 运营区：对账和结算的查询、详情与按能力启用的动作。
- 能力对照区：统一业务目标、两端现状、兼容方式和后端迭代清单。

商户操作、渠道模拟和平台运营使用明确标签或视图切换。危险、资金结果或人工裁决动作需要确认；普通查询不增加确认。

桌面和移动视口均须可用。标识、错误和源诊断允许换行或复制，按钮和状态不能因动态内容改变固定工具区尺寸或互相遮挡。

## 6. 状态、错误和异步处理

每个请求显示局部加载状态并防止重复提交。无数据、能力不可用、HTTP 404、业务冲突、字段错误、网络不可达和超时必须区分。

异步轮询有最大次数、间隔和用户可见状态；超时后保留已受理回执和资源 ID，允许用户手动刷新，不把超时改写为业务失败。

标准错误展示统一消息，并提供可展开的源错误码、源消息和关联信息。可重试操作显示重试入口，不可重试冲突引导用户修改输入或查看现有资源。

## 7. 本地最近记录

本地存储只保存最近访问资源的最小导航信息：资源类型、ID、显示标签、最近访问时间、适配器配置标识和可选状态摘要。切换适配器时默认只显示对应配置的记录，避免把一个后端的 ID 发给另一个后端。

用户可以移除本地记录或清空本地历史。任何位置都不得称其为“全部订单”“交易列表”或后端分页结果。

## 8. 能力和后端对齐清单

工作台和文档维护同一组对齐主题：

| 主题 | 统一业务目标 | WOW 当前 | CAP4K 当前 | 工作台当前处理 | 后端后续对齐 |
|---|---|---|---|---|---|

## 9. 文档

README 必须说明项目结构、安装与启动、两种模式、后端地址、代理配置、统一模型、适配器结构、业务流程、能力差异、第三适配器步骤、已知限制和验证命令。

独立对齐文档必须展开第 8 节主题，引用两个后端的实际入口或缺口，并区分“业务目标、当前实现、工作台兼容、后端待办”。

## 10. 运行和验证边界

项目采用轻量、成熟的前端工具链，不引入大型 UI 框架或全局状态管理基础设施。开发模式通过同源代理连接本地后端，至少提供清晰的 WOW 与 CAP4K 启动命令。

自动化验证覆盖统一模型与映射边界；浏览器验证覆盖主要页面、典型流程、状态反馈和响应式布局。没有真实后端运行时，可以使用 mock transport 验证前端契约，但不得把 mock 结果宣称为后端业务能力证据。

## 11. 明确非目标

本规格不修改两个后端，不实现生产认证、安全签名、真实支付网络、生产通知、权威后台列表、跨币种、分账、订阅、预授权撤销、争议或税务。模板尚未冻结的业务政策只作为待决项展示，不由工作台设定默认资金规则。
