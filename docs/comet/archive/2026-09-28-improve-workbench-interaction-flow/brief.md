# 目标

修复支付参考工作台中已经由真实操作暴露出的交互断层，使不了解前端实现的学习者能够清楚看到命令是否被拒绝、是否已经受理、Operation 是否仍在观察、当前操作绑定哪一个资源，以及动作完成后权威详情和列表是否已经更新。

本 change 继续保持页面与后端实现无关。WOW 与 CAP4K 的读取收敛、状态和 transport 差异仍由统一服务、适配器和资源 `actions` 吸收；页面只按统一资源、稳定 ID、Attempt 状态和动作描述渲染交互。

# 范围

- 为同步业务错误、网络错误和观察错误提供固定在当前视口内的可关闭通知；通知展示稳定错误码和摘要，页面内继续保留完整 details、correlationId、源诊断与安全重试入口。
- 统一“命令提交 → receipt 受理 → Operation 观察 → 权威资源回读 → 关联列表刷新”的交互流程；命令成功、继续观察后收敛以及投影稍后可读时，都自动更新当前详情和相应权威列表，不要求用户手工刷新整页。
- 区分命令同步拒绝与命令已受理后的观察/读取失败；后者必须保留 receipt、Operation ID 和继续观察能力，不能误报为命令未执行。
- Payment、Refund、ReconciliationRun、Settlement、ManualReviewItem 以及通知等详情入口以列表行稳定 ID 为导航依据，打开时调用权威详情查询；列表摘要不得直接冒充完整详情。
- 防止快速切换列表项时旧请求覆盖后选详情；详情加载期间展示局部加载状态并保持当前筛选上下文。
- 将支付与退款的所有 attempt/submission/result 表单状态绑定到当前 Payment ID 或 Refund ID。切换资源时清空旧 Attempt、渠道、外部交易号、结果 identity 和其他依赖字段，并为新资源生成新的命令 identity；同一命令的安全重试继续使用原 identity。
- 正常业务路径使用真正的 Attempt 选择器，只显示当前允许提交或接收结果的已知 Attempt；只有一个可选项时自动选中。未知 Attempt 引用保留为显式开启的“异常实验”模式，不与常规选择混在同一个自由输入控件中。
- 选择 Attempt 时级联更新渠道和外部交易号/渠道退款号；所选 Attempt 缺少字段时清空对应值，禁止残留上一 Attempt 的关联数据。异常实验模式允许用户明确覆盖这些值。
- 创建、提交和可信结果区域以只读方式显示当前绑定的 Payment ID 或 Refund ID，不再要求用户猜测隐式上下文，也不新增可编辑的资源 ID 输入框。
- 根据完整资源及 Attempt 事实生成统一 `actions`：已有未提交或在途 Attempt 时禁止再次创建并说明下一步；只允许提交可提交 Attempt；只有明确可重试失败且策略允许时才重新开放创建。后端实现差异必须停留在 adapter/action 映射层。
- 同步修复支付和退款页面中跨资源复用幂等键、Submission ID、Result identity 以及列表详情陈旧导致的关联错误，并把共性刷新、通知和详情加载能力复用于对账、结算、人工核对和通知页面。
- 补充组件、服务、adapter/action 和页面测试，并分别通过真实 WOW 与 CAP4K 验证支付与退款代表性流程、同步业务错误和 Operation/投影收敛刷新。

# 非目标

- 不修改 `wow-reference-payment`、`cap4k-reference-payment` 或 `payment-product-template`；真实联调若发现新的后端缺陷，只保存可复现证据并另行处理。
- 不改变支付、退款、对账、结算、人工核对、通知或 timeline 的统一业务含义，也不绕过后端状态迁移、幂等和可信结果边界。
- 不把每个普通错误改成阻塞式确认弹窗；危险业务动作仍使用现有确认机制，普通请求反馈使用非阻塞通知和持久页内诊断。
- 不引入大型 UI 框架、全局状态管理库或通用设计系统；继续使用现有 React、TypeScript 和轻量样式结构。
- 不新增后端 API、生产认证授权、持久化可靠性、真实渠道或其他生产强化设施。

# 验收示例

唯一验收清单定义在完整目标规格 `specs/payment-workbench/spec.md` 的 15 个 `Scenario:` 中。与本 change 直接相关的重点为：支付和退款 attempt 闭环、五类权威详情、业务表单与上下文级联、错误/观察反馈，以及真实 WOW、真实 CAP4K 和双后端规范化一致性；其余场景用于确认本次共享交互重构没有破坏既有统一业务能力。

# 约束与不变量

- 页面、组件和 hooks 只能依赖统一服务、统一领域对象与 `actions`，不得读取 adapter kind、拼接后端路由或出现 WOW/CAP4K 业务条件分支。
- receipt 只表示命令受理；HTTP 2xx、`ACCEPTED`、Operation 成功和资源业务成功必须继续分层展示。
- 自动刷新必须读取后端权威详情和列表，不能用本地乐观拼接伪造 Attempt、receipt、状态、预算或业务终态。
- 列表行是摘要和导航入口，不是权威完整详情；详情读取失败时保留已选资源 ID和错误上下文，不回退到陈旧摘要冒充成功。
- 资源上下文切换时必须隔离表单身份和关联值；同一命令因网络/观察问题安全重试时必须保留原幂等身份。
- 已知 Attempt 的自动级联不得覆盖服务端事实；异常实验必须显式开启，并继续经过后端可信边界和业务裁决。
- `ActionDescriptor` 的可执行性、禁用原因和刷新/观察策略是页面动作的唯一依据；无法统一的传输差异由 adapter 映射，不得让用户通过试错发现后端规则。
- 固定通知不得遮挡关键操作，必须支持键盘和屏幕阅读器；关闭通知不能删除页内持久诊断、receipt 或 Operation 上下文。
- 保持 Money、finality、opaque cursor、退款预算、对账阻断、结算冻结、防重复资金操作和完整 timeline 等既有不变量。

# 决策

- 普通错误采用固定在视口内的非阻塞 toast/notice，并使用 `aria-live` 及时播报；页面原位置保留可展开的完整 `ErrorBlock`。只有需要用户确认的危险动作继续使用 dialog/confirm。
- 共性刷新由统一命令执行和详情加载机制承载，各页面只声明资源读取与列表失效范围，不分别复制一套轮询和错误处理。
- 列表“详情”先以稳定 ID建立选择上下文，再读取权威详情；使用请求序号或取消机制确保最后一次选择获胜。
- 正常 Attempt 选择与未知引用实验拆成两个明确模式。常规模式使用 `<select>` 并级联字段；异常模式使用独立自由输入并给出风险说明。
- 表单命令 identity 以“当前资源 + 动作步骤”为生命周期边界：切换资源生成新值，同一资源的同一次重试保持不变，命令明确成功后为下一动作生成新值。
- 创建 Attempt、提交 Attempt 和可信结果表单都显示当前目标资源 ID；该 ID来自权威详情上下文，只读不可编辑。
- 支付与退款动作由完整资源及 Attempt 状态推导；有未决 Attempt 时优先引导提交、等待或处置现有 Attempt，不允许再创建并行资金尝试。
- 本 change 使用单个 Native change。共享命令反馈、详情加载、Payment/Refund 级联和真实双后端验收相互依赖，拆分会增加状态与刷新契约漂移。

# 待解决问题

- 无阻塞问题。用户已授权前端技术方案由实现者决定；固定通知、权威回读、上下文隔离和显式异常实验均可从现有业务诉求与代码事实可靠确定。

# 验证预期

- Runtime 正式检查至少执行 TypeScript 类型检查、现有及新增 Vitest 测试和 production build；`git diff --check` 必须通过。
- 单元/组件测试覆盖固定错误通知、持久诊断、命令拒绝与观察失败分层、READ_ONCE/POLL 投影延迟、继续观察后详情及列表刷新，以及快速切换详情的竞态保护。
- 支付和退款页面测试覆盖：列表摘要与权威详情不同、切换有/无 Attempt 的资源、唯一可提交 Attempt 自动选择、多 Attempt 选择、关联字段清空/回填、异常模式、资源 ID只读绑定、幂等身份隔离与安全重试。
- action/adapter 测试覆盖已有未决 Attempt 时禁建、可提交 Attempt 筛选、明确可重试失败后重新开放，以及 WOW/CAP4K 差异不泄漏到页面。
- 对账、结算、人工核对和通知页面验证点击详情读取权威数据、动作后自动刷新以及错误在当前视口可见。
- 分别启动真实 WOW 与 CAP4K，从干净 reference fixture 经真实 HTTP 完成至少一条支付和部分退款流程；验证创建/提交 Attempt 后无需手工刷新即可看到权威 Attempt/receipt，并验证一个稳定业务错误的通知与持久诊断。
- 双后端真实验收不得修改、清理或提交两个后端工作树；允许内部 ID、路由、HTTP 方法和 readAfter 模式不同，只比较统一业务观察与交互结果。
