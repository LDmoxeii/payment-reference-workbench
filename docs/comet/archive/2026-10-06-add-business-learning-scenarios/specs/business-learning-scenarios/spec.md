# 业务场景学习手册

## 目标与交付

为 Reference Payment Workbench 提供中文 `docs/business-learning-scenarios.md`，从 README 抽取业务练习，帮助学习者理解页签、表单、按钮、输入与自动处理的分工。README 保留运行和架构概要，增加手册入口，长篇重复操作教程使用概要与手册链接衔接。

文档覆盖环境准备、成功支付、部分退款、账单与对账、漏账纠正、结算、差异处置、UNKNOWN 与人工核对、通知、时间线及两项可选练习。所有业务能力继续由现有系统提供，此规格只增加文档。

## Requirement: 页签与阅读方式

手册按实际导航解释首页、支付、退款、对账、结算、人工核对、Reference Lab、实现对照。首页说明连接状态和业务地图；人工核对页同时包含通知；Payment Timeline 从支付页进入；实现对照只读展示统一含义及能力差异，不承担交易命令。

每个场景统一包含目的、前置条件、页签/表单/按钮、手填或需确认的输入及其来源、自动生成/预填/处理、顺序步骤和逐步预期结果、完成判据及下一步。核心表单要能找到用途和场景入口，不能只列字段名。

共用说明区分 HTTP/receipt 受理、Operation 状态、权威资源业务状态和 finality；说明观察暂未完成时继续同一个 Operation 或权威回读。自动预填不代替点击提交。五类权威列表及通知列表说明筛选、应用、清空、分页、打开详情和刷新；条件变化回首屏，最近记录只作快捷入口。

### Scenario: 新学习者定位页签、输入与动作

- GIVEN 学习者已打开工作台，尚不了解页签或表单
- WHEN 阅读手册导航、共用规则与任意一个场景
- THEN 能找到全部八个页签、通知与 Timeline 的位置，以及每个核心表单/按钮对应的用途或场景
- AND 每个场景具有规定的结构，明确用户输入/核对、自动预填及点击后自动处理的责任
- AND 共用列表和异步说明不会把最近记录当权威列表、把受理当业务成功或把预填当自动执行
- AND README 和手册相互链接，场景链接/锚点有效，深入实现说明链接保留

## Requirement: Reference 环境

环境练习说明 fixture、merchant、channel、actor alias、policy、逻辑时钟和业务时区的用途，使用首页/刷新环境读取当前配置，再根据练习需要登记或设置；不默认重置既有环境。

Reference Lab 说明环境/策略表单、设置和推进时钟、账单编辑器、维护任务以及 payment channel、bill provider、notification sender、settlement executor 四类脚本。列明配置/读取/重置各自作用、脚本定位输入及消费动作；配置脚本本身不发起支付或执行结算。对能力 full/alternative/unavailable 如实说明，缺独立诊断读取接口不意味着脚本没有业务消费能力。

### Scenario: 准备环境并理解 Reference Lab

- GIVEN 已运行工作台及选定的 WOW 或 CAP4K 后端
- WHEN 按环境练习查看配置、理解必要表单和脚本、准备本次业务日
- THEN 能识别需填写/确认的环境参数与自动回读数据，按逻辑时钟和时区选取日期
- AND 明确刷新不会改写手工或历史行时间，显式同步时间需要核对影响范围
- AND 四类脚本的配置、诊断、重置及消费步骤都有说明，WOW/CAP4K 不同定位方式和诊断能力准确
- AND 说明这是学习与确定性复现工具，可信结果由服务端裁决，不提供 verified=true 输入或生产能力承诺

## Requirement: 成功支付

支付练习说明商户、订单号、金额/币种、支付方式、到期时间和幂等键；默认/生成值仍需核对。按“创建但不自动发起”→创建 attempt→选择并提交 attempt→接收可信结果顺序推进。

Lab 可准备渠道脚本，提交可信结果的表单实际在支付页。注明渠道、外部交易号、发生时间和结果的来源，不要求把学习示例当真实证据。成功后回查 receipts、Operation、PaymentSuccessFact、费用快照、通知和 Timeline 入口，并简述 FAILURE/UNKNOWN 的下一步。

### Scenario: 按四个独立动作完成支付

- GIVEN 已准备环境及一个本次独立订单
- WHEN 阅读成功支付练习并顺序定位创建、attempt 创建、attempt 提交和可信结果表单
- THEN 每步写明必要输入、默认值、按钮文字及权威预期结果
- AND 不声称创建支付自动创建/提交 attempt，或配置脚本已等于付款
- AND 成功完成以权威支付事实与业务状态判断；外部号来自实际成功详情
- AND FAILURE/UNKNOWN 的预算或核对含义按资源类型说明，不复制异常组合矩阵

## Requirement: 部分退款

退款练习以已成功支付为前提，说明权威预算 original/succeeded/reserved/available、来源 Payment ID、商户退款身份、金额/币种、原因和幂等键。申请预占后独立创建/提交 RefundAttempt，再接收可信结果并回查预算。

用部分退款示范，说明全额退款使用当时可用额度，步骤共用。成功转换预占，明确失败释放相应预占，UNKNOWN 保留预占并进入相应核对；退款外部号与支付外部号分开。

### Scenario: 申请退款并读懂预算变化

- GIVEN 一笔有可用退款额度的成功支付
- WHEN 阅读部分退款练习及全额退款说明
- THEN 能定位预算、申请、attempt 和结果表单，区分用户金额/原因与自动生成或预填身份
- AND 每步说明预占、成功转换、失败释放、UNKNOWN 保留的权威结果
- AND 以本次 Refund 的渠道退款号和状态作为后续账单输入，不从支付号推造退款号

## Requirement: 完整账单与匹配对账

账单练习解释平台事实与渠道账单核对的目的，以及 Bill ID、revision、行 ID、外部交易号的不同身份。每版是完整不可变快照；支付和退款独立行，金额单位为元，内部精确转换，业务日依逻辑时钟与业务时区。

按编辑→确认完整发布→权威回读→前往对账并核对上下文→通知可用/运行→检查结果顺序写步骤。缺账单权威 merchant 时需要用户确认本次商户。导航只预填，不运行。

WOW 通知账单可用仅验证/回读账单，之后独立创建 Run；CAP4K 信号动作会产生或推进 Run，先查看回读结果，避免写成两端都必需再次创建。说明运行对账是计算/形成权威匹配和差异证据，MATCHED 无需人工处置，筛选只改变显示。WOW 在权威允许时可以显式完成，CAP4K 可自动完成；是否结算以权威候选、资格和原因码判断，不能宣称整个 Run 必须 COMPLETED 才能结算。

### Scenario: 发布完整账单并读懂对账完成

- GIVEN 已有真实支付/退款成功事实及其外部号
- WHEN 阅读账单发布与匹配对账练习
- THEN 发布、可见、导航、通知、运行、匹配、完成及结算资格被区分，逐步预期结果明确
- AND 记录输入来自实际事实，发布核对 Bill ID/revision/行数，暂未读出时继续同一观察或回读
- AND WOW/CAP4K 的信号及完成动作说明与当前实现一致，不隐式重复创建 Run
- AND MATCHED 只查看证据，零差异仍检查完整性、未解决/阻断明细及权威结算资格

## Requirement: 漏账纠正

使用隔离商户/渠道/币种/业务日范围中的三笔100元支付和一笔20元退款作教学示例；使用者替换为实际金额、外部号、时间与本次独立 ID，不固定用户账单或电脑日期。

revision 1 故意只含一笔支付，隔离示例 Run 为4/1/3；说明 PLATFORM_ONLY。查询历史版本、复制整版为新草稿，以权威 currentRevision+1 生成版本，添加/复制行并核对真实外部号，形成包含全部四行的完整 revision。再次发布、回读和运行，有效新 Run 为4/4/0；旧版/旧 Run 保留，不累加快照。计数只是对应隔离示例，不推广到有其他交易的环境。

### Scenario: 用完整新版本纠正漏账

- GIVEN 教学范围存在三笔成功支付和一笔成功退款，旧版只含一笔支付
- WHEN 阅读查询、复制整版、补齐行、完整发布及重新对账步骤
- THEN 能理解旧4/1/3与新4/4/0的来源，并根据实际范围核对权威计数
- AND 每个新 revision 包含全部交易，退款独立一行；添加/复制行生成身份但不会替用户选择另一笔真实交易号
- AND 历史只读，版本号取 currentRevision+1，原版及旧 Run 不被覆盖
- AND 回读有效新 Run 后检查资格，再接入结算练习

## Requirement: 成功结算

说明 prepare 的商户/币种/周期、included/excluded 候选和原因码；收入、退款、费用、调整及净额由权威候选计算。用户核对构成后确认冻结 scope/items/Money/version，再准备相应 executor 脚本、执行并查看权威结果。

脚本按当前后端所需 fixture/channel 或 executionId 定位，用户核对原执行身份及执行渠道。SUCCESS 只对应一次成功事实；UNKNOWN 保持原 execution，不得新发付款；明确 FAILURE 后也须权威允许才可新执行。净额不写死280或278.20，不将“完成所有 Run”当通用硬前提。

### Scenario: 从候选到冻结再到成功结算

- GIVEN 本次交易范围的权威候选允许相应结算动作
- WHEN 阅读准备、检查构成、确认冻结、脚本配置和执行步骤
- THEN 每步指出输入、自动候选/计算、按钮及权威结果，冻结与执行分开
- AND 完成以实际构成、净额及唯一成功 execution/业务事实为准
- AND SUCCESS/FAILURE/UNKNOWN 的后续限制准确，未知结果不能触发新的付款身份

## Requirement: 差异处置与事实确认

以真实差异为前提解释 difference 类型、matching basis、平台/渠道双方证据、未解决和阻断范围。DifferenceDisposition 与 FactConfirmation 分别说明适用条件、结果与所需 actor/reason/evidence 及关联事实。

练习至少给出一种有证据支持的差异处置路径及事实确认的适用说明，随后检查追加历史、原始事实和相应阻断。不能要求把差异全部接受以继续结算，不能处置 MATCHED。

### Scenario: 对真实差异作责任处置

- GIVEN Run 中存在需要判断的真实差异，且权威动作允许处置或事实确认
- WHEN 阅读差异练习并核对双方证据、责任字段与结论
- THEN 能区分 DifferenceDisposition 与 FactConfirmation，并找到各自输入和适用动作
- AND 默认 reason/evidence 只作输入示例，要求使用实际检查后的依据
- AND 预期结果为追加处置历史和权威阻断变化，原始账单与平台事实保留

## Requirement: UNKNOWN 与人工核对

提供一条典型 UNKNOWN→关联核对→读取证据与 blocking scopes→选择权威允许 outcome→填写责任与证据→确认处置→回查历史的练习。支付、退款、结算的 UNKNOWN 含义分别概括，负净额说明关联核对入口，不展开所有 outcome 组合。

商户、actor alias/ID/role、reason、evidence、补救引用和幂等身份的默认值需检查；KEEP_ACCEPTED_SUCCESS 等需补救引用时按当前要求填写。结论与解除阻断由后端裁决，处置不抹除历史。

### Scenario: 处理未知结果而不重复资金动作

- GIVEN 支付、退款或结算资源关联一个权威人工核对项
- WHEN 阅读 UNKNOWN 练习并沿稳定关联 ID 打开核对详情
- THEN 能找到 outcome、责任、原因、证据及必要补救引用的来源和操作
- AND 区分退款仍占额度、结算仍保留 execution 身份等结果，不以重复尝试替代核对
- AND 处置后查看权威业务状态、解除的具体阻断及追加历史，不承诺人工按钮必然把业务变为成功

## Requirement: 通知

通知练习从实际成功事实或关联资源定位 notification，读取 content identity、来源与投递历史。需要演示重试时说明 Lab sender 脚本定位和投递结果，再按权威动作重试原通知并观察新投递尝试。

### Scenario: 查看通知并重试原投递

- GIVEN 已有权威通知及可查看的投递历史
- WHEN 阅读通知查询、sender 配置和重试练习
- THEN 每步说明输入来源、自动回读及对应按钮，失败/未知投递不等于业务失败
- AND 明确重试仅重新投递同一业务内容，不重复支付、退款或结算
- AND 按权威详情观察新增投递历史，不把列表摘要当完整证据

## Requirement: 时间线

在支付页通过本次 Payment ID 读取 Timeline，说明 occurredAt 与 recordedAt 的区别及 recordedAt ASC、eventId ASC 稳定顺序；解释自动读取分页后的关联资源、责任、证据、支付、退款、账单/Run、结算、通知和人工事件。

### Scenario: 从支付时间线回查闭环

- GIVEN 一笔经历相关业务动作的支付
- WHEN 阅读支付页“读取 Timeline”练习
- THEN 能找到入口并理解自动分页、排序、两种时间与关联 ID
- AND 根据本次实际发生的事件回查各权威资源，不宣称每笔支付必然已有全部流程事件

## Requirement: 可选练习

将到期关闭和结算作废/replacement 列为两个可选练习，沿用统一模板。到期练习说明逻辑时钟、维护任务及单支付关闭的不同用途，只在权威动作允许时关闭。作废/替代说明原因/证据、原 Settlement 与替代关联，按权威动作限制推进，不能绕过 SUCCESS/UNKNOWN 或 scope 唯一性。

### Scenario: 按条件执行到期关闭或结算替代

- GIVEN 支付已满足到期条件，或 Settlement 权威动作允许作废/创建 replacement
- WHEN 阅读相应可选练习
- THEN 前置条件、所需输入、实际按钮、自动结果与完成判据完整
- AND WOW/CAP4K 的单独或组合传输差异被转为可理解的操作说明
- AND 不要求学习者改变现有成功事实、重付 UNKNOWN、清空数据或逐项构造边界异常

## 验证与范围限制

文档核对使用现有 README、当前 UI/适配器及已调查后端契约；检查全部场景和输入责任、两端差异、Markdown 链接/锚点及 `git diff --check`。不安装依赖、不运行新的资金实验、不操作用户账单，不改任何业务代码。来源覆盖与不纳入的边界实验在 brief 中逐条记录。
