# 目标

交付一套可运行的支付业务工作台。工作台以后端实现无关的统一业务诉求为准，通过适配器分别连接 `wow-reference-payment` 与 `cap4k-reference-payment`，用于理解支付到结算的业务流程、对照两个实现、演示现有闭环，并快速验证后续业务诉求。

后端当前能力只决定某个动作现在是“可执行、部分可执行或待对齐”，不得反向缩减统一业务模型。工作台应把当前差异显式呈现，并产出可执行的后端对齐清单。

# 范围

- 建立统一领域模型、请求/响应模型、状态语义、错误模型、分页模型、操作回执和能力声明。
- 建立统一服务接口、HTTP 客户端与适配器工厂；页面和业务组件只依赖统一服务与能力/动作声明。
- 实现 WOW 与 CAP4K 两个适配器，封装路径、方法、字段、金额、响应、状态、错误、异步收敛及流程差异。
- 实现业务工作台：首页与连接状态、支付创建和查询、支付详情与尝试/渠道结果、退款、对账、结算、全链路/能力对照。
- 商户操作、渠道模拟、平台运营三个视角在同一工作台中明确分区；渠道模拟只调用后端真实提供的 reference/sandbox 入口。
- 支持加载、空状态、网络错误、业务错误、字段错误、异步轮询、幂等复用提示和源状态查看。
- 两套后端均没有权威列表接口时，以本地最近记录提供导航，同时明确其不是后端全量列表；统一契约仍定义分页查询目标。
- 通过集中配置和独立启动模式切换两个适配器，不修改任何页面代码。
- 提供 README 和后端对齐文档，说明现状、差异、工作台兼容策略、后续后端迭代及新增第三适配器步骤。

# 非目标

- 本 change 不修改 `wow-reference-payment` 或 `cap4k-reference-payment`；后端对齐项另行迭代。
- 不把 reference/sandbox 渠道、账单、通知或资金划拨描述为生产级支付能力。
- 不实现真实认证授权、商户开户、真实渠道签名、银行卡/钱包网络、清算或真实资金移动。
- 不伪造后端没有提供的权威列表、分页、订单内容、交易数据、对账批次或结算结果。
- 不决定模板尚未冻结的退款期限、人工核对时限、双人复核阈值、周结、负结算额追偿等业务政策；工作台只显示后端事实和待对齐状态。
- 不支持跨币种、分账分润、订阅扣款、预授权撤销、拒付/争议和税务能力。
- 不在本 change 内建设生产部署、生产监控或生产安全体系。

# 验收示例

## Scenario: 统一业务契约与适配器隔离

**Given** 工作台分别使用 WOW 或 CAP4K 配置启动，**When** 用户进入同一组业务页面，**Then** 页面只调用统一服务并依据统一能力/动作声明渲染；切换后端不修改页面代码，源路径、字段、状态、金额和错误差异均由适配器处理。

## Scenario: 创建和查询支付

**Given** 用户填写商户、订单号、幂等键、精确金额、币种、支付方式和可选到期时间，**When** 提交创建并查询返回的支付号，**Then** 页面显示统一支付详情、源状态、幂等复用结果和可执行动作，且金额不经过 JavaScript 浮点计算。

## Scenario: 支付尝试与渠道结果收敛

**Given** 某支付在当前适配器下存在可执行的支付动作，**When** 用户发起尝试或通过渠道模拟提交成功、失败、未知、重复或冲突结果，**Then** 工作台按该后端实际流程执行、轮询最终读模型，并分别展示支付主状态、尝试状态、回执处置与证据；不把“已受理”显示为成功。

## Scenario: 退款闭环

**Given** 支付已成功且存在可退款金额，**When** 用户创建全额或部分退款并按当前适配器支持的方式推进结果或人工裁决，**Then** 工作台显示退款状态、源状态、成功/占用/可退款金额和错误原因，并可从支付详情追踪相关退款。

## Scenario: 对账、结算与全链路操作

**Given** 当前适配器声明了某项对账、结算或追踪能力，**When** 用户按 ID 查询或执行该适配器公开的重跑、处置、准备、确认、执行、结果、替代或裁决动作，**Then** 页面使用统一业务视图显示事实、证据、阻断原因和可执行动作；未支持的动作明确显示待对齐原因而不发送虚假请求。

## Scenario: 状态、错误与异步反馈

**Given** 请求可能加载、为空、失败、冲突、未找到或最终一致收敛，**When** 任一情况发生，**Then** 页面保持输入和上下文，展示标准化错误码、可读消息、字段问题、是否可重试及源诊断，并为异步操作显示受理与最终状态的区别。

## Scenario: 最近记录与列表缺口

**Given** 两个后端当前都没有权威支付/退款列表和分页接口，**When** 用户创建或成功查询业务对象，**Then** 工作台把其 ID 写入浏览器最近记录并支持再次打开，同时显著说明这不是后端全量列表；统一分页契约和两个后端的实现缺口出现在对齐清单中。

## Scenario: 业务能力与后端对齐清单

**Given** 统一业务诉求和两个后端现状存在差异，**When** 用户查看能力对照页或维护者阅读对齐文档，**Then** 能逐项看到目标业务语义、WOW 现状、CAP4K 现状、工作台当前兼容方式、缺失能力、建议后端改动和优先级，至少覆盖列表/分页、支付发起流程、退款结果流程、对账入口、结算流程、轨迹、认证授权与浏览器接入。

## Scenario: 工作台交互可用性

**Given** 用户在桌面或移动视口使用工作台，**When** 在商户操作、渠道模拟和平台运营流程间导航并提交表单，**Then** 页面信息层次清楚、控件不重叠、长标识可阅读、危险或不可逆动作有明确确认，加载/空/错误/成功反馈不会引发布局跳变。

## Scenario: 可运行与可扩展交付

**Given** 开发者获得仓库，**When** 按 README 安装并分别运行 WOW、CAP4K 模式，**Then** 应用可启动、构建和测试，代理连接对应后端；README 说明目录、配置、切换、统一契约、流程、差异、限制及新增第三适配器的步骤。

# 约束与不变量

- 业务目标以 `payment-product-template` 为准，后端差异不能进入页面条件分支。
- 资金金额使用精确字符串/最小单位表示；禁止以 JavaScript 浮点作为领域金额真源。
- 统一状态与源状态并存；渠道回执处置不得覆盖资源生命周期状态。
- HTTP 命令成功只表示受理时，工作台必须继续查询读模型，不把受理等同于终态成功。
- 只调用后端真实存在的入口；未实现能力通过 capability/action 声明和对齐清单表达。
- 本地最近记录只用于导航，不能被描述为后端权威列表。
- 不丢弃源错误码、源状态、源标识和诊断信息，统一后仍应便于学习与排错。
- 同一套页面和组件必须可连接两个适配器；新增后端以新增适配器、映射和配置为主。
- 开发期通过同源代理连接后端；当前没有 CORS/生产认证的事实必须如实说明。

# 决策

- 采用“统一目标契约 + 后端能力声明 + 可执行动作”的模型，而不是取两个后端接口交集。
- 首期覆盖支付、退款、对账、结算与追踪；每项按后端实际能力提供完整、部分或只读/待对齐体验。
- 工作台按“商户操作 / 渠道模拟 / 平台运营”组织交互，避免把测试回调伪装成商户业务动作。
- 两个后端没有列表时使用明确标注的本地最近记录，同时把列表/分页列为高优先级后端对齐项。
- WOW 的隐式启动尝试和 CAP4K 的显式启动尝试均由统一动作模型兼容；目标业务仍保留独立支付尝试语义。
- 不要求用户决定前端技术细节；技术选择以轻量、成熟、可维护和最小依赖为原则。
- 本需求使用单个 Native change；统一契约、适配器、页面和文档共享同一模型，拆成 Supervisor 子 change 会增加契约漂移成本。

# 待解决问题

- 无阻塞问题。模板中尚未冻结的业务政策作为“业务待决/后端待对齐”展示，不由本工作台替业务方暗中决定。

# 验证预期

- 静态检查覆盖 TypeScript 类型、代码质量和生产构建。
- 自动化测试覆盖金额转换、状态映射、错误映射、能力声明、两个适配器的请求/响应映射和关键业务流程状态。
- 使用 mock HTTP 数据验证同一页面在两个适配器下的创建、查询、结果推进、退款和能力降级。
- 启动开发服务器，使用浏览器分别检查桌面与移动视口的主要流程、加载/空/错误状态、无重叠和可读性。
- 不主动安装新依赖；若工作区没有依赖缓存，保留完整 manifest/lockfile 并执行无需安装即可完成的静态验证，明确未运行项。
