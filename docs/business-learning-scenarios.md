# 业务场景学习手册

这份手册帮助你理解工作台的页签和表单，再按“前置条件 → 输入 → 操作 → 预期结果”完成业务练习。它是学习操作指南，不是边界测试矩阵。启动方式、架构与完整能力概要见 [README](../README.md)，深入实现差异见 [后端对照](./backend-alignment.md)。

## 阅读顺序

第一次使用，先读页签地图和共用规则，再做练习 01–04、06：准备环境 → 支付 → 可选退款 → 完整账单和对账 → 结算。练习 05 演示漏账纠正；练习 07–10 帮助理解运营处置与追溯；练习 11–12 是可选分支。

| 练习 | 你将学会什么 | 依赖 |
| --- | --- | --- |
| [01 环境与时钟准备](#scenario-01) | 看懂 Reference Lab，确定商户、渠道与业务日期 | 已启动工作台和所选后端 |
| [02 成功支付](#scenario-02) | 区分创建支付、创建 attempt、提交 attempt、接收结果 | 01 |
| [03 部分退款](#scenario-03) | 看懂申请预占和退款预算变化 | 02 的成功支付 |
| [04 完整账单与匹配对账](#scenario-04) | 发布账单、通知可用、运行对账、理解匹配与完成 | 02；有退款时包括 03 |
| [05 用完整新版本纠正漏账](#scenario-05) | 保留旧版证据，用完整新 revision 修正遗漏 | 独立范围的三笔成功支付和一笔成功退款 |
| [06 准备、冻结与成功结算](#scenario-06) | 核对候选构成，再冻结和执行 | 04 或 05 的权威结算资格 |
| [07 真实差异处置与事实确认](#scenario-07) | 判断差异、追加责任处置、理解 FactConfirmation | 有真实差异的当前有效 Run |
| [08 UNKNOWN 与人工核对](#scenario-08) | 沿关联核对项处理不确定结果 | 未知结果及已产生的权威核对项 |
| [09 通知查看与重试](#scenario-09) | 回查业务通知，重试原投递 | 已有通知 |
| [10 Payment Timeline](#scenario-10) | 从一笔支付追溯实际发生的闭环 | 已有 Payment ID |
| [11 可选：到期支付关闭](#scenario-11) | 用逻辑时钟理解到期与维护 | 独立的未完成支付 |
| [12 可选：结算作废与 replacement](#scenario-12) | 看懂原结算与替代结算的关系 | 权威动作允许的独立结算 |

下文使用本次练习的实际 ID。`Payment ID`、`Refund ID`、`Bill ID` 等都是你从权威详情记录的值，不是让你照抄的固定示例。请使用独立教学范围；不要为练习清空已有数据，也不要改写已有成功事实。

## 八个页签分别做什么

| 页签 | 用途 | 主要表单、按钮及其效果 | 对应练习 |
| --- | --- | --- | --- |
| 首页 | 看连接状态、当前环境和业务地图 | 刷新环境读取配置；业务地图卡片进入相应页签 | 01 |
| 支付 | 创建支付并推进独立 attempt；查看支付事实、预算、收据、费用 | 创建支付；创建/提交 attempt；Reference 渠道结果；关闭到期支付；读取关联通知；读取 Timeline | 02、09–11 |
| 退款 | 对成功支付申请退款，查看预算和退款 attempt | 来源支付/预算查询；申请并预占退款预算；创建/提交 attempt；提交可信退款结果 | 03、08 |
| 对账 | 把平台交易事实与渠道账单逐笔核对，形成匹配和差异证据 | 查询账单/Run；通知账单可用；创建 ReconciliationRun；差异处置/FactConfirmation；重跑；显式完成 | 04、05、07 |
| 结算 | 按资格计算商户待结算构成，冻结后执行 | 准备结算候选；责任字段；确认并冻结；发起新 execution；提交结算结果；作废/创建替代 | 06、12 |
| 人工核对 | 处理需责任判断的业务问题，并查看商户通知 | 查询人工核对；提交责任处置；查询通知；重试通知。通知就在这个页签中 | 08、09 |
| Reference Lab | 准备可复现的学习环境和模拟渠道输入 | Fixture 与 Policy；逻辑时钟；四类脚本；多记录账单 revision；运行到期与维护任务 | 01、04、05及各练习的脚本准备 |
| 实现对照 | 只读理解统一业务含义和两端能力差异 | 查看对照与能力说明，不提交交易命令 | 遇到能力提示时参考 |

**Reference Lab 是实验准备区。** 配置“下一次成功”不会自动创建支付，配置结算脚本不会自动付款，发布账单也不等于运行对账。可信支付/退款结果的提交表单实际在支付/退款页；结算执行及结果表单在结算页。

## 所有练习共用的读图规则

### 谁填写，谁处理

| 内容 | 用户负责 | 页面或后端负责 |
| --- | --- | --- |
| 业务输入 | 确认商户、订单/退款身份、金额、币种、渠道、时间范围及本次业务意图 | 校验输入，返回权威资源 |
| 默认值和生成身份 | 核对环境预填、生成的幂等键、attempt/submission/execution 身份；记录本次实际值 | 生成默认值、按所选资源预填关联字段；成功操作后可能生成下一份表单值 |
| 渠道结果 | 学习环境中选择要模拟的结果；核对渠道外部号和实际发生时间 | 服务端验证可信来源并裁决结果；前端没有可编辑的 `verified=true` |
| 人工责任 | 用实际检查填写 actor、结论、原因、证据及必要补救引用 | 校验权限与适用条件，追加处置历史，重新计算相关阻断 |
| 候选金额/资格 | 检查纳入、排除及原因是否符合本次范围 | 计算费用、调整、净额、资格和允许动作，不能靠改显示值解除阻断 |

“已经预填”只表示可供核对，不表示已经执行。不同步骤是独立命令，仍需点击对应按钮。幂等键标识同一个业务意图；观察尚未完成时继续同一个 Operation，不以新身份重复资金动作。

### 四层状态要分开看

| 层次 | 告诉你什么 | 不能由它直接推断什么 |
| --- | --- | --- |
| HTTP / OperationReceipt | 请求被受理、关联哪个资源及 Operation | 支付或结算已成功 |
| Operation | 这条命令是否完成、失败或仍在处理中 | 完成的命令一定产生 SUCCESS；记录 UNKNOWN 的命令也可能执行成功 |
| 权威资源业务状态与事实 | Payment、Refund、Run、Settlement 实际发生了什么 | 匹配数等于全部资格检查 |
| finality 与 actions | 事实是否已确定、当前允许做什么、为什么阻断 | 列表摘要或按钮预填可以替代权威判断 |

页面按后端的观察方式回读 Operation 和资源。若显示暂未收敛，点击“继续观察同一 Operation ID”（部分位置简称“继续观察同一 Operation”），或刷新同一个权威详情。账单无 Operation 回执时用“继续回读已发布账单”。不要把等待窗口结束当成业务失败。

### 权威列表的共同操作

支付、退款、ReconciliationRun、Settlement、ManualReviewItem 是五类权威列表；人工核对页还有通知列表。浏览器“最近记录”只是快捷入口，不是完整业务数据。

1. 输入商户、状态、finality、稳定资源 ID、创建时间区间，以及该列表特有的条件；点“应用筛选”才按这些条件查询。
2. “清空”清除筛选并回到首屏；应用新条件也回首屏，不沿用旧页位置。通知列表共用相同筛选控件，未提供的类型专属条件不要自行推造。
3. “上一页/下一页”沿用后端返回的分页位置；用户不用填写 cursor，也不要根据本页行数推断总数。
4. “详情”回读权威资源；核对其 ID、业务状态、证据、历史与 actions。“刷新本页”更新当前列表页，详情的刷新图标更新当前详情。

### 练习记录建议

保留一份简单记录：当前后端、fixture、商户、渠道、币种、逻辑时间、业务时区/业务日期；本次 Payment/Refund/Bill/revision/Run/Settlement/execution ID；支付和退款各自的成功外部号、金额及发生时间。后续表单从这些实际记录取值。

业务日按 **Reference 逻辑时钟 + 所选业务时区**确定，不直接使用电脑今天。练习不固定业务日；例如选择 `Asia/Shanghai` 时，应核对逻辑时间在该时区属于哪一天。

## 练习 01：环境与时钟准备

**目的：** 确定当前练习范围，并理解 Lab 每个核心表单的用途。

**前置条件：** 工作台及选定的 WOW/CAP4K 后端已启动；运行方式见 README。当前环境能回读，不需要重新安装依赖。

**页签/表单/按钮：** 首页、Reference Lab；刷新环境、Fixture 与 Policy、逻辑时钟、四类脚本、多记录账单 revision、运行到期与维护任务。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| Fixture ID、商户、渠道、Actor alias | 从当前环境读取；需要新环境时确认所选后端支持的配置和隔离范围 | Lab 回读后预填；fixture 标识不保证两端都有独立数据空间 |
| 支付到期时长、UNKNOWN 复核时长、Reference 费率 | 核对本次策略，时长用 ISO-8601 duration，例如 `PT30M` | 默认只是示例；资源实际阈值和费用快照以后端回读为准 |
| 绝对时间、推进时长 | 仅在练习确实需要时填写 ISO 时间或 duration，例如 `PT10M` | 读取逻辑时钟；提交设置/推进后更新后端时间 |
| 业务时区、业务日 | 在账单/对账/结算范围中核对，来自逻辑时间和业务口径 | 新账单行预填当前逻辑时间；刷新不改写手填或历史行时间 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 在首页读取连接与当前环境，再打开 Lab 刷新环境 | 明确当前后端、fixture、商户、渠道、时钟和能力；连接正常才能继续 |
| 2 | 核对环境是否已经满足练习；仅需要初始化/变更时点“登记环境与策略”并确认 | 回读登记结果。CAP4K 此入口还初始化共享 policy、clock、渠道脚本和通知脚本，因此已有可用环境时跳过，不把它当刷新按钮 |
| 3 | 需要时间练习时用“设置时钟”或“推进时钟”；随后刷新环境 | 逻辑时间与本次意图一致；设置与推进是两个写操作 |
| 4 | 记录业务时区和由此得到的业务日；核对账单/对账的日期默认值 | 时间范围有明确来源。对账“从逻辑时钟同步业务日期”只同步其日期输入；账单“同步业务日期与全部行时间”会先确认影响范围 |
| 5 | 阅读下表，选择后续练习所需的脚本；没有用途的脚本不用配置/重置 | 能区分配置、诊断、重置与业务消费；此时尚未支付、退款或结算 |

### 四类脚本怎么用

| Lab 表单 | 定位输入与来源 | 配置按钮的作用 | 哪个业务动作消费它 |
| --- | --- | --- | --- |
| 渠道提交脚本 | 当前 fixture/渠道，选择成功、失败、UNKNOWN、提交拒绝或“受理但不返回结果” | “应用下一次提交脚本”准备渠道观察；能力为替代时显示“获取替代实验路径” | 支付或退款页“提交 attempt”；选 NO_RESULT 可再用对应结果表单手动演示可信收件 |
| 账单 provider 脚本 | 已发布 Bill ID、revision、暂不可读次数 | “配置 provider 读取脚本”控制读取可见性，不发布另一份账单；正常主线使用 0 次 | 账单权威回读、通知可用及对账读取 |
| 通知 sender 脚本 | 本次 Notification ID，或权威来源类型/来源事实 ID | “应用通知脚本”准备下一次投递结果 | 业务产生通知后的投递或人工核对页“重试通知” |
| 结算 executor 脚本 | 结算页实际选用的渠道和期望 Execution ID；结果 SUCCESS/FAILURE/UNKNOWN/NO_RESULT | “应用结算脚本”准备执行观察，不发起付款 | 结算页“发起新 execution” |

“回读脚本与消费诊断”查询所选脚本的配置、消费状态；“重置脚本”改变该脚本配置，不撤销历史业务事实。只对明确选中的练习配置使用重置。

WOW 四类脚本均可配置/读取/重置，渠道和结算脚本按 fixture/渠道定位，通知按通知或来源定位，账单按 Bill/revision 定位。CAP4K 渠道可配置/重置但无独立诊断读取；账单暂不可读次数随发布 revision 登记，独立 provider 配置/读取/重置不可用；通知可配置/重置但无独立诊断读取；结算按 Execution ID 配置/读取/重置。页面仍需核对渠道和 Execution ID，适配器选择实际绑定。

能力提示中，`full` 表示支持该控制面，`alternative` 表示按页面提示走替代路径，`unavailable` 表示当前诊断或控制动作不可用。缺诊断读取接口不等于脚本不能被业务消费。

“运行到期与维护任务”也有差异：CAP4K 当前工作台调用的是支付到期检查；退款/结算 UNKNOWN 的阈值复核由相应后端任务负责，这个按钮没有逐类任务选择。WOW 当前返回替代路径说明，不执行一项通用维护命令。到期关闭见练习 11，UNKNOWN 见练习 08。

**完成判据：** 已记录当前环境、逻辑时间及业务范围，知道哪些按钮修改配置、哪些业务按钮才推进交易。Reference 是学习和确定性复现工具，不代表生产渠道、真实资金或完整权限系统。

**下一步：** 练习 02；已有成功支付时可从练习 03 或 04 继续。

<a id="scenario-02"></a>
## 练习 02：完成一笔成功支付

**目的：** 看懂四个独立动作，并取得后续退款/账单需要的实际成功事实。

**前置条件：** 练习 01 已完成；有可用商户/渠道/支付方式及本次独立订单。为看清四步，可先在 Lab 将渠道脚本设为“受理但不返回结果”；若使用成功脚本，提交 attempt 后可能已经自动收到成功观察。

**页签/表单/按钮：** 支付 → 创建支付、创建 attempt、提交 attempt、Reference 渠道结果；Lab 只用于准备脚本。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| 商户、商户订单号、金额、币种、支付方式、到期时间 | 商户/方式来自环境；订单号代表本次订单；金额如 `100.00` 元，币种和到期时间按本次意图确认 | 商户、订单号、方式和幂等键可能预填；到期策略由后端裁决 |
| Attempt ID、幂等键、风控原因 | Attempt ID 可选；方式与原因按实际需要；核对当前 Payment ID | ID 可由后端生成；页面生成默认幂等键 |
| Attempt、Submission ID、幂等键 | 选择刚创建且可提交的 attempt，保留本次提交身份 | 下拉来自权威 attempts，默认 submission 身份可生成 |
| 结果、渠道、Result identity、外部交易号、发生时间、失败处置 | 学习主线选 SUCCESS；外部号来自渠道/已提交 attempt，没有返回时补充本次模拟渠道号；时间对应这次结果；失败处置仅在FAILURE时按实际结论填写 | 渠道和已有外部号随所选 attempt 预填，Money 来自 Payment；服务端完成可信验证 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 核对创建字段，点“创建但不自动发起” | 得到 Payment ID 和权威详情；尚未自动创建或提交 attempt |
| 2 | 在本 Payment 的“创建 attempt”表单提交 | 权威 attempts 出现本次 Attempt ID；尚未等于渠道成功 |
| 3 | 在“提交 attempt”选择该 attempt，点“提交 attempt” | 出现 submission receipt/提交状态。NO_RESULT 留待结果收件；成功脚本可能已推进到成功，先回读 |
| 4 | 若尚无成功事实，在结果表单选择已提交 attempt，核对关联字段与 SUCCESS，点“提交可信结果（不可编辑 verified）” | 可信结果由后端裁决并追加 result receipt；已被脚本成功处理时跳过，避免把重复收件当必做步骤 |
| 5 | 回读 Payment，查看成功事实、attempt 收据、费用规则快照；点“读取关联通知” | 业务成功与 PaymentSuccessFact 对应；记录实际成功外部号、金额、币种及发生时间；通知投递状态单独判断 |

**完成判据：** 权威支付业务状态和成功事实确认这笔支付成功；不能只凭 Operation SUCCEEDED。费用按实际快照读取，外部号从成功详情记录。Timeline 入口在同一支付页。

**下一步：** 练习 03 退款，或练习 04 账单。FAILURE 时回查失败原因及允许动作；UNKNOWN 仍未确定成功/失败，按练习 08 查关联核对，不能把新 attempt 当确认原结果的方法。支付 UNKNOWN 没有退款申请所说的“预占退款预算”含义。

## 练习 03：申请部分退款并读懂预算

**目的：** 理解申请时的预占与最终退款结果的关系。

**前置条件：** 一笔成功支付有可用退款额度；准备本次独立商户退款号。需要手动结果演示时先配置渠道 NO_RESULT。

**页签/表单/按钮：** 退款 → 来源支付/退款预算、申请退款、创建 attempt、提交 attempt、Reference 退款结果。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| 来源 Payment ID、商户 | 从成功支付详情取得，查询后核对归属 | 回读 `original / succeeded / reserved / available` 预算 |
| 商户退款号、金额、币种、原因、幂等键 | 退款身份属于本次申请；例如在100元可用额度中申请20元；原因来自退款意图 | 商户/币种和默认身份可能预填；额度校验由后端完成 |
| Attempt/Submission 身份 | 独立创建再选择提交，使用本 Refund 的 attempt | 身份生成及关联下拉与支付类似 |
| 结果、渠道退款号、时间 | 主线 SUCCESS；渠道退款号来自本次退款提交，不使用支付外部号 | 渠道/已有退款号预填；退款金额来自 Refund，服务端验证结果 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 查询来源支付并读预算 | `original` 是原支付金额，`succeeded` 是已成功退款，`reserved` 是仍占用的申请，`available` 是当前可申请额度 |
| 2 | 核对金额、原因和身份，点“申请并预占退款预算” | 生成 Refund ID，预占增加、可用额度相应减少；尚未证明钱已退回 |
| 3 | 为该 Refund 点“创建 attempt”，再选择它点“提交 attempt” | 形成独立 RefundAttempt 与 submission receipt；脚本可能自动给出结果，先回读 |
| 4 | 尚未成功时点“提交可信退款结果”，核对 SUCCESS 与本次渠道退款号 | 追加 result receipt，成功事实将该笔预占转换为成功退款 |
| 5 | 刷新 Refund 和来源支付预算 | 本次退款金额计入 succeeded，不再同时保留为本次 reserved；记录实际渠道退款号和发生时间 |

全额退款共用这套步骤，金额取**当时权威 available**，不能忽略其他成功退款或未决预占。明确 FAILURE 释放相应预占；UNKNOWN 保留预占，达到复核条件后查看关联人工核对。预算示例只适用于没有其他退款的隔离支付。

**完成判据：** 本 Refund 的权威成功事实、渠道退款号与预算变化一致。

**下一步：** 练习 04；未知退款按练习 08 处理。

**目的：** 用渠道账单核对平台事实，区分发布、可见、通知、运行、匹配、完成和结算资格。

**前置条件：** 本次范围内已有成功支付，有退款时也记录其成功事实；已取得真实外部号、金额、币种和发生时间。

| WOW | 通知只验证/回读账单；随后在“运行对账”表单点“创建 ReconciliationRun” | 有独立完成命令；权威允许时提交，Run状态据此更新 |
| CAP4K | 信号路径可创建或推进Run；先查看Operation关联资源、回读Run及列表。已有本次有效结果时不用再次创建；确需运行/重跑才执行对应动作 | 没有额外complete命令；账单完整且差异/阻断解除后服务端自动收敛，页面提供观察路径 |

## 练习 05：用完整新版本纠正漏账

**目的：** 理解 PLATFORM_ONLY 和不可变账单版本，使用补齐的新快照恢复核对。

**前置条件：** 本次范围有权威可结算事实，相关阻断已按业务处理；准备一个尚未付款的独立结算范围，不重复结算已经成功的scope。

## 练习 07：处理真实差异，并理解 FactConfirmation

**目的：** 用双方证据支持责任结论，理解“接受差异”与“新增确认事实”。

**前置条件：** 当前有效Run及revision存在真实差异，权威动作允许处置。漏账的正常修正先用练习05；MATCHED不是差异处置对象。

**页签/表单/按钮：** 对账 → 对账明细、差异证据与追加历史、差异处置/FactConfirmation、提交责任处置。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| Difference ID、Merchant ID、revision | 从当前有效Run选择真实差异，核对归属和版本 | Difference ID随选择预填且只读；双方证据和matching basis来自后端 |
| 处置类型、结论、结算影响 | 根据实际证据决定；证据不足的本练习选DifferenceDisposition、ESCALATE、BLOCK | 后端验证适用性并重算阻断；界面选择不能自行授权 |
| actor alias/ID、原因、证据引用、幂等键 | 责任身份来自授权环境；原因写真实检查结论，引用实际账单行、平台事实或渠道调查依据 | actor role来自页面责任上下文；默认文本不是已经存在的证据 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 在有效Run选择一条真实差异，读difference类型、matching basis、平台与渠道状态、证据 | 知道差在哪里、哪些事实缺失，记录实际关联资源和阻断范围 |
| 2 | 以“当前证据尚不足以判定可结算”为教学路径，选择DifferenceDisposition、继续升级并保持阻断、BLOCK | 结论与证据相符；不为了继续流程一律选择ALLOW |
| 3 | 用实际原因和证据替换默认文本，核对责任和幂等身份，点“提交责任处置” | 受理后观察同一Operation，权威历史追加本次处置 |
| 4 | 回读差异、Run及关联核对 | 原账单与平台事实保留；本路径仍阻断，需要继续调查或版本纠正，不能宣称已可结算 |

DifferenceDisposition记录“如何对待这条差异”。证据足够且权威允许时，可选择“接受差异并保留原事实”，再按真实业务判断ALLOW/BLOCK；它本身不等于补造一笔成功事实。FactConfirmation则追加“经授权、基于渠道证据的平台确认事实”，用于其适用的缺失/状态不一致情形。

FactConfirmation适用说明：例如当前有效Run有CHANNEL_ONLY或STATUS_MISMATCH，渠道证据确为成功，金额、币种、交易类型、外部号及商户/渠道归属都可核实，才考虑“FactConfirmation + 确认平台事实 + 形成确认结算事实（CONFIRM）”。它不适用于把PLATFORM_ONLY漏账或MATCHED强制确认，关联Payment/Refund也必须有真实依据。回读应出现确认事实及追加历史；是否解除具体阻断仍由后端判断。

**当前表单限制：** CAP4K确认路径从权威差异证据构造确认内容并校验归属；WOW需要完整确认事实内容，而当前页面只传结论，未提供金额、币种、交易类型、外部号等完整内容的填写入口。因此本手册只说明WOW的适用条件，不承诺其当前FactConfirmation表单可完成提交。出现该限制时保留原阻断及证据，不能通过编造字段或接受所有差异绕过。相关实现位置见文末。

**完成判据：** 完成一条有实际依据的责任处置，能回查追加历史、原始事实及具体阻断。FactConfirmation只有在完整证据和当前能力满足时才算完成，不能凭按钮被点击推断。

**下一步：** 证据不足继续调查或练习05；已允许结算的事实按练习06重新检查候选资格。

<a id="scenario-08"></a>
## 练习 08：UNKNOWN → 关联人工核对

**目的：** 处理未确定结果，保留原资金身份，并理解人工按钮的责任含义。

**前置条件：** 独立学习资源有UNKNOWN结果，并已关联一个权威ManualReviewItem。下面以退款未知结果为例；若尚未生成核对项，先按实际阈值和后端任务观察，不能假定提交UNKNOWN立刻产生Review ID。

**页签/表单/按钮：** Lab渠道脚本；退款结果及详情；人工核对 → 查询人工核对、提交责任处置、确认处置。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| UNKNOWN结果及关联身份 | 沿原Refund/Attempt提交或消费UNKNOWN，不重申请同一笔退款 | 记录未知结果，保留相应预算预占 |
| 复核阈值、逻辑时间、Review ID | 从权威attempt/资源读取reviewAfterAt或实际策略；Review ID来自资源关联或按关联ID筛选权威列表 | 达到阈值后相应后端任务可生成核对项；不是由用户随意起一个Review ID |
| Outcome、商户、actor alias/ID/role、原因、证据、幂等键 | 根据当前核对类型和实际调查选择允许结论；确认失败需真实失败依据 | 责任/原因/证据可能预填为示例，后端验证并追加历史 |
| 补救引用 | 选择“保留已接受成功并记录补救”（KEEP_ACCEPTED_SUCCESS）时按实际补救记录填写 | 必要字段校验；不凭空生成已经完成的补救 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 独立申请退款并创建/提交attempt，脚本选UNKNOWN，或按练习03的结果表单收件UNKNOWN | 结果未定，reserved仍占用；命令已执行不等于退款成功 |
| 2 | 读取关联核对；尚无核对项时核对阈值，在隔离练习需要时推进逻辑时钟，再观察后端复核任务 | 达到实际条件才会出现权威核对项。CAP4K的Lab维护按钮不触发退款复核；WOW按钮只给替代说明，不能写成“点维护必然生成” |
| 3 | 到人工核对页按真实Review ID查询，或按关联资源ID筛选列表打开详情 | 看见类型、原业务资源、evidenceRefs、blocking scopes和既有处置；确认不是别的交易 |
| 4 | 有实际失败依据且当前类型允许时选择“确认失败”，核对责任字段并填真实原因/证据，点“确认处置” | 后端裁决结论、追加处置。依据不足时可升级并保持阻断，不应为了完成练习自报失败或成功 |
| 5 | 回读核对历史、原Refund及来源支付预算 | 只把权威接受的业务结论和对应预算变化作为结果；核对项被解决不必然意味着任意资源都变成SUCCESS |

UNKNOWN在三类资源的含义不同：支付尚未确定支付结果；退款继续占预算；结算保留原execution，不能新付款。负净额结算等问题也从关联核对项读取证据和阻断，其处置不是强制执行负净额付款。

**完成判据：** 针对实际核对项追加了有依据的允许结论，能回查原业务状态、处置历史及解除或保留的具体阻断；没有通过重复资金动作猜测原结果。

**下一步：** 依据权威结论继续相应业务，或保持阻断等待调查；练习09/10回查通知和时间线。

<a id="scenario-09"></a>
## 练习 09：查看通知并重试原投递

**目的：** 看懂通知身份和投递历史，区分业务结果与通知投递结果。

**前置条件：** 支付/退款等实际事实已产生通知。重试练习选择本次独立通知；已有成功投递时只查看即可，无需把它改造成失败。

**页签/表单/按钮：** 支付 → 读取关联通知；人工核对 → 查询通知、商户通知投递历史、重试通知；Lab → 通知sender脚本。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| Notification ID、content identity、业务资源 | 从关联通知或权威列表取得，核对内容确属本次事实 | 详情回读来源及每次attempt，不靠列表摘要判断全部历史 |
| 脚本Notification ID或来源类型/来源事实ID、下一次结果 | 使用实际通知/来源，演示成功重试时选SUCCESS | WOW按fixture与selector；CAP4K按通知或来源selector绑定 |
| 重试商户、幂等身份 | 核对原通知归属；保持同一待观察命令 | 页面以原通知生成重试命令，追加投递attempt |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 支付页点“读取关联通知”，记录实际ID；在人工核对页查询或从通知列表打开详情 | 读取notification/content identity及投递历史 |
| 2 | 区分SUCCESS/FAILURE/RESULT_UNKNOWN投递状态，检查attempt时间与诊断 | 投递失败/未知不撤销支付或退款成功事实 |
| 3 | 需要重试时，在Lab定位原通知或真实来源，选SUCCESS并点“应用通知脚本” | 只配置下一次投递结果，还没有重新投递 |
| 4 | 返回原通知，点“重试通知”并观察同一Operation，再刷新详情 | 后端处理重投递；实际执行新投递时出现新增attempt，原通知内容身份与历史保留 |

**完成判据：** 原通知和业务事实可对应，实际投递结果/新增历史有权威依据。通知重试只是重新投递同一业务内容，不重复支付、退款或结算。

**下一步：** 练习10追溯完整关联。

<a id="scenario-10"></a>
## 练习 10：用 Payment Timeline 回查闭环

**目的：** 从一笔支付回查实际发生的业务与人工事件。

**前置条件：** 已有本次Payment ID；可以只完成支付，也可以已经经历退款、账单、对账、结算和通知。

**页签/表单/按钮：** 支付 → 查询支付、其他动作与全链路Timeline、读取Timeline。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| Payment ID | 取本次支付权威详情，先确认选中正确支付 | 页面读取该支付的Timeline |
| 事件资源ID、责任、证据 | 用事件中的实际关联ID到对应页签查询 | 自动沿分页读取并按稳定顺序展示；用户不用填cursor |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 查询本次支付，点“读取 Timeline” | 页面读取关联事件，包含当前实际已经发生的步骤 |
| 2 | 比较occurredAt与recordedAt | occurredAt是业务发生时间，recordedAt是平台记录时间；两者可能不同，展示按 `recordedAt ASC, eventId ASC` 稳定排序 |
| 3 | 查看支付/attempt、退款、账单/Run、结算、通知和人工事件中实际存在的关联 | 自动分页后的结果用于追溯；没有做过的环节不应被期待必然出现 |
| 4 | 用事件的关联ID回查相应权威详情、责任和证据 | 能把业务事实、后续动作与追加历史串起来，不把事件标题当完整详情 |

**完成判据：** 能解释这笔支付已发生的顺序、两种时间和关联资源，并回查关键证据。

**下一步：** 主线学习结束；需要了解正常可选分支时读练习11/12。

<a id="scenario-11"></a>
## 练习 11：可选的到期支付关闭

**目的：** 理解时间推进、到期检查与单支付关闭的不同作用。

**前置条件：** 独立未成功支付具有明确到期时间，逻辑时间已达条件；权威actions允许相应处理。不使用已有成功支付做关闭练习。

**页签/表单/按钮：** Lab → 逻辑时钟、运行到期与维护任务；支付 → 关闭到期支付。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| 到期时间、逻辑时间、推进duration | 从该Payment实际到期时间确定需要推进多少，考虑共享环境影响 | 时钟变更更新后端时间，不等于所有资源立即被关闭 |
| Payment ID、关闭动作 | 原支付详情，先核对状态与允许动作 | 后端按到期与未决attempt判断关闭或关联核对，不由用户指定最终状态 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 创建独立未发起支付，读取实际到期时间 | 有可回查的目标Payment与时间条件 |
| 2 | 必要时在Lab推进逻辑时钟，再刷新Payment | 到期条件已满足；只推进时间还不是关闭命令 |
| 3 | 权威允许时点“关闭到期支付”；需要查看批量检查时参考Lab维护说明 | WOW/CAP4K都有单支付关闭动作；CAP4K维护做支付到期检查，WOW维护入口返回替代说明，不能当作批量关闭已执行 |
| 4 | 观察Operation并回读原Payment、关联核对/历史 | 无未决渠道结果的目标按权威规则关闭；有未决attempt时可能要求核对，不能强制当成普通关闭成功 |

**完成判据：** 原Payment的权威关闭结果或需要核对的结论与实际条件一致；未改写已成功事实。

**下一步：** 有关联核对则练习08，否则练习10查看事件。

<a id="scenario-12"></a>
## 练习 12：可选的结算作废与 replacement

**目的：** 理解撤销候选和创建替代结算的关联，按当前权威动作选择路径。

**前置条件：** 独立Settlement处于允许作废/替代的状态，原因和证据齐全；没有SUCCESS或UNKNOWN等禁止新付款的事实，也不能绕过scope唯一性。

**页签/表单/按钮：** 结算 → 责任字段、确认冻结/作废/替代、作废、创建替代。

| 输入及来源 | 用户需填写或核对 | 自动预填/处理 |
| --- | --- | --- |
| 原Settlement ID与当前状态 | 从权威详情和actions确认当前能做的动作 | 按descriptor展示/禁用按钮并提供原因 |
| actor alias/ID/role、原因、证据、幂等键 | 真实作废/替代意图和授权责任；默认文本需替换 | 校验约束，追加责任记录 |
| replacement身份、前后继关系 | 从实际回执/原详情取替代ID | 页面生成替代请求身份；后端建立原结算→替代结算关系 |

| 步骤 | 操作 | 逐步预期结果 |
| --- | --- | --- |
| 1 | 查询原Settlement，检查状态、scope、execution事实与actions | 不满足条件时停止该可选练习，读取阻断原因，不靠新ID绕过 |
| 2 | 核对责任字段及真实原因/证据，选择当前允许的动作 | 只是撤销时用“作废”；需要替代时按下表，不能统一要求先作废 |
| 3 | 确认所选动作并观察权威回读 | 原结算状态及替代关联按所选操作变化，历史保留 |
| 4 | 有替代结算时用实际替代ID查询，重新核对候选和允许动作 | 替代不是原结算成功的复制，不自动执行付款 |

| 后端 | 正常操作说明 |
| --- | --- |
| WOW | 需要替代时，在原结算仍持有效范围、尚未作废且权威动作允许时，直接点“创建替代”；该命令会作废原结算并建立替代链。只需撤销时才单独点“作废”，已单独作废的结算不能再走创建替代路径 |
| CAP4K | 当前允许的“创建替代”组合完成作废原候选及创建replacement；应在可执行该动作的原状态直接选择它。先单独作废后不能假定还能再调用组合动作 |

**完成判据：** 原Settlement的实际状态、追加责任与前后继关系可回查，替代资源独立检查；没有重复执行UNKNOWN或已成功结算。

**下一步：** 确认替代候选满足资格时按练习06推进，或只保留作废结果。
